# 사전 정의한 내용 정리

## 1. Descriptor Selector

모델을 학습하며 다음과 같은 자동화를 수행코자 합니다.
1. 주어진 데이터에서의 필요/불필요/애매함 descriptors를 계산합니다. (RDKit 사용)
2. 애매함 descriptor에 대해서는 HITL 및 외부 도구(RAG, MCP 등)를 적용하여 해결합니다.
3. 이를 바탕으로 모델 재학습을 자동화하여, descriptor를 이용한 다양한 태스크에서의 성능을 향상시키고자 합니다.

### 가설
- descriptor를 선택하는 과정이 명시적이고, 이를 바탕으로 모델 재학습을 자동화한다면, 필요시 descriptor 수정이 가능하고, 이를 통해 다양한 태스크에서의 성능을 향상시킬 수 있을 것이다.
- Feature selection과 feature learning을 결합(hybridize)하면 descriptor set이 상호보완적 정보를 가질 때 모델 정확도가 개선된다는 연구가 이미 존재합니다. [1]
- "명시적 분류 + HITL + 자동 재학습" 조합이 기존 embedded/wrapper 방법 대비 우위가 있다는 것은 아직 검증되지 않은 새로운 주장입니다.
- 모델 학습은 당연히 많이 하기 때문에, 신약 개발에서의 병목 현상을 줄일 수 있다.

### 구현 방안
- 애매함 판정은 기존의 존재하는 Feature Selection 알고리즘으로 실행. 

### 논의 필요성

#### LLM 검증 루프에서의 평가 방법론
- LLM 검증 루프를 설계함에 있어서, human-in-the-loop 방식과 fully automated 방식을 비교하여, descriptor를 분류하는 방식에서의 문제점을 해결할 수 있을 것이다. 다만 판단이 옳았는지 ablation study나 permutation importance를 통해 검증해야 한다[4].
- LLM 에이전트가 불확실성이 높은 지점에서만 HITL 체크포인트를 두는 방식은 최근 신약 개발 AI 파이프라인에서 실제로 쓰이는 설계입니다. [5]

#### 기존 방법론과의 비교
- 기존의 Boruta, RFECV, LASSO/RF importance 같은 기존 embedded/wrapper 방법들과 비교하여 실제로 예측 성능이 개선한다는 근거를 보일 필요성이 있다.
- Boruta는 Random Forest 기반 wrapper 방법으로 shadow feature와 Z-score 비교를 통해 유의미한 feature를 확정하며, 실제 비교 연구에서 mRMR보다 훨씬 적은 수의 feature를 선택하는 경향이 확인됐습니다. [3]

#### 모델 학습이 신약 개발에서의 실제 병목인가?
- 신약 개발의 실제 병목은 계산/모델링 단계가 아니라 합성(synthesis)과 실험적 검증(experimental validation) 단계라는 것이 업계 컨센서스에 가깝습니다.
- DMTA(Design-Make-Test-Analyze) 사이클에서 속도를 제한하는 요인은 화합물을 실제로 합성하고 테스트(wet-lab)하는 데 걸리는 시간이며, 계산 설계 속도가 아무리 빨라져도 합성이 병목으로 남는다는 지적이 다수입니다. [2]

## 2. Descriptor Generator 

주어진 데이터를 학습하여 새로운 descriptors 가설을 생성하고 검증합니다.
이를 통해 기존의 descriptor를 개선하거나 새로운 descriptor를 추가하여 모델의 성능을 향상시킵니다. 

1. 외부 문헌을 참고하여 새로운 descriptor 가설을 생성합니다.
2. 내부 데이터를 참고하여 새로운 descriptor의 유효성을 검증합니다.
3. 필요시 외부 도구를 통해 새로운 descriptor를 구현합니다.
4. descriptor를 이용한 모델 학습 데이터셋을 구축합니다.

### 가설
- 1번 주제에 이어, 생성형 모델을 활용하여 새로운 descriptor를 생성하고자 한다. 
- 내부 데이터와 문헌을 바탕으로 생성형 모델이 새로운 descriptor 가설을 생성하고 검증한다면, 기존의 descriptor를 개선하거나 새로운 descriptor를 추가하여 모델의 성능을 향상시킬 수 있을 것이다.

### 구현 방안
- 생성형 모델을 활용하여 새로운 descriptor를 생성하고자 한다.

### 논의 필요성

#### 1) 새로운 descriptor의 발견에 대한 가능성? 
- 화학구조에서 뽑아내는 "특징값"(디스크립터)들, 예를 들어 LogP(기름에 잘 녹는 정도), TPSA(극성 표면적), 분자량 같은 건 이미 1990말에 체계화되었으며 [1], 신약개발 분야에서는 거의 모든 논문에서 이미 최대 1000~2000개 정도를 기본적으로 사용한다[2]. 이러한 특징값들은 EDA를 통해 정제되어 모델에 적용된다.
- 딥러닝(Graph Neural Network 등)을 쓰면 이런 수작업 디스크립터를 굳이 계산 안 해도 되지만, 장점도 확실하다. interpretability(해석 가능성)가 좋고, 계산이 빠르다[3]. LLM도 똑같이 "문자열(SMILES)"에서 특징을 추출하는 것일 뿐이므로, RDKit만으로는 못 잡는 복잡한 패턴을 학습할 여지는 분명히 있다. 단, "새롭고 혁신적인" 디스크립터를 만들려면, 그냥 기존 것만 잘 섞는 수준이 아니라 뭔가 차원이 다른 아이디어가 필요할 수 있다.
- AI가 분자 구조를 보고 스스로 특징을 뽑아내는 방식(그래프 신경망, ChemBERTa 같은 사전학습 모델)으로 연구 흐름이 넘어갔습니다. 실제로 ChemBERTa는 SMILES(분자 표기법) 7,700만 개를 학습해서 기존 방식보다 예측 성능을 5~10% 끌어올린다는 보고도 있습니다[4].
- 다만 간독성(DILI)이나 CYP450 대사처럼 특정 목적에 딱 맞는 지표는 지금도 조금씩 새로 제안됩니다[5]. 예를 들어 평균분자량(AMW) 같은 지표가 간독성 여부를 가르는 데 유용하다는 연구가 최근에도 나옵니다.

#### 2) 어떤 descriptor을 생성해야 하는가?
- 문헌에서 다뤄지는 특징값들은 매우 다양하다. 
- LogP나 TPSA는 2D-QSAR 표준으로 광범위하게 다뤄진다 [1]. 반면 순수 위상학적 지수(Chi3v 등)는 "이 지수를 넣었더니 모델 성능이 올랐다"는 식으로만 언급되지, "왜 생물학적으로 의미 있는지"를 따로 설명한 논문은 거의 없습니다.

#### 3) descriptor 변경시 모델을 모두 재학습해야 하는데..
- 재학습해야죠
- 그런데 QSAR 데이터셋은 수천~수만 개 화합물 수준이라 RF/GBM/LASSO 재학습의 부담이 크지 않다는 의견 [3]
- 재학습 시, nested CV를 다시 돌려서 새 피처셋이 실제로 성능을 개선했는지 확인해야 함. QSAR 분야에서는 이중/중첩 교차검증(double/nested CV)이 데이터를 효율적으로 쓰면서 모델 선택과 성능 평가를 분리하는 권장 방법으로 문헌에 명시돼 있다. [6]

#### 4) 추가의견
- 그래서 문제가 되는 지점: AI(특히 RAG, 즉 논문을 검색해서 근거로 삼는 시스템)한테 "이 디스크립터가 논문에서 뒷받침되는가"를 기준으로 걸러내라고 하면, 유명한 디스크립터만 계속 살아남고(마태 효과)[7] 덜 유명한 디스크립터는 실제로 유용해도 "근거가 없다"는 이유로 부당하게 탈락할 수 있다[8].

## 3. Automated EDA Tool

주어진 타겟 데이터셋에 대한 분석 자동화를 통해 연구자들의 보조자로서 데이터를 해석하고, 가설 생성 및 검증을 수행합니다. 

### 가설
- 데이터를 해석하고, 가설을 생성하는 것을 통해 연구자들의 병목현상을 줄일 수 있다.

### 구현 방안
- 데이터셋을 읽고 분석하고, EDA 결과를 시각화하여 LLM에게 전달한다. 

### 논의 필요성
- LLM에게 데이터를 해석하라고 하면 어떻게 해야 하는가?
- EDA 결과를 LLM에게 전달할 때, 어떤 방식으로 전달해야 하는가?
- 시각화 자료를 LLM에게 전달할 때, 어떤 방식으로 전달해야 하는가?

## 4. Automated Model Builder — 신약 개발 모델 자동 생성 및 최적화
 
주어진 데이터셋과 사용자 요청(예측할 endpoint, 컴퓨팅 자원, 해석 가능성 요구 수준 등)을 바탕으로 모델 학습 코드를 자동 생성·실행하고, 검증 루프를 통해 최적의 모델을 스스로 찾거나 기존 모델을 개선하는 독립 시스템.
 
### 가설
 
- "주어진 데이터셋과 목적에 대해, 어떤 분자 표현 방식·알고리즘·하이퍼파라미터 조합이 가장 신뢰할 수 있는 예측 성능을 내는가"이다. 특정 조합을 미리 정해두지 않고, 여러 후보를 실제로 학습·검증한 결과로만 채택 여부를 판단한다.
- 다만 이 시스템이 제공하는 가치는 "매번 학습 코드를 새로 생성하는 것"이 아니라 "후보 탐색·검증·채택을 오케스트레이션하는 것"에 있다. 앞선 검토에서 확인했듯 AutoML 도구(H2O AutoML, auto-sklearn, TPOT)와 QSAR 특화 도구(QSARtuna)가 이미 알고리즘·하이퍼파라미터 탐색과 CV 기반 채택을 자동화하고 있으므로 [1][2], 이 시스템의 차별점은 알고리즘 탐색 자체를 재발명하는 데 있지 않고 도메인 특화 탐색공간(분자 표현 선택, descriptor 필터링 로직)과 사람 승인 계층을 통합하는 데 있다. 코드 생성이 실제로 필요한 시점은 완전히 새로운 endpoint를 다루거나 알고리즘/아키텍처 자체를 바꿀 때로 한정된다.

### 탐색 공간 (Search Space)
 
- **분자 표현**: 손으로 설계한 디스크립터(RDKit/Mordred) vs 학습된 표현(ECFP fingerprint, GNN embedding, 사전학습 언어모델 파인튜닝). 데이터 규모가 작고 해석 가능성이 중요하면 전자, 데이터가 충분하고 성능이 우선이면 후자 쪽 후보 비중을 높임. 실제로 descriptor 기반 모델(RF, XGBoost)은 대형 데이터셋에서도 수 초 내 학습되고 SHAP 등으로 해석이 용이한 반면, GNN 계열은 정확도·효율성에서 descriptor 기반 모델에 못 미치는 경우가 많다는 비교 연구 결과가 이 선택 기준을 뒷받침한다 [3].
- **피처 선택**(디스크립터 기반 선택 시): VIF(분산팽창지수) 기반으로 다중공선성이 심한(통상 VIF>5~10) 변수를 우선 정리하는 unsupervised 단계를 거친 뒤 [4], Boruta나 재표본(resampling) 기반 stability selection으로 CV 안전하게 변수를 선택한다. Boruta는 Random Forest 기반 wrapper 방법으로 shadow feature와의 Z-score 비교를 통해 유의미한 feature만 확정하는 방식이 문헌으로 확인된다 [5].
- **알고리즘**: RF, GBM, Elastic Net, (데이터 충분 시) GNN/MLP
- **하이퍼파라미터**: 각 알고리즘별 탐색 범위 정의

### 구현 방안
 
#### 1) 모델 학습 루프
 
1. 입력: 원본 데이터셋(SMILES + endpoint 라벨), 사용자 요청
2. 탐색공간에서 후보 조합(표현×알고리즘×하이퍼파라미터) 샘플링
3. 각 후보를 nested CV로 평가 — outer는 성능 평가 전용, inner에서 피처선택/하이퍼파라미터 탐색을 수행해 leakage 차단. 이는 QSAR 모델 선택·평가에서 데이터를 효율적으로 쓰면서 편향을 줄이는 권장 방법으로 문헌에 명시돼 있다 [6].
4. CV 성능 분포(평균±표준편차) 기준으로 후보 비교, 성능 차이가 노이즈 수준이면 더 단순하고 해석 가능한 모델을 우선 채택
5. 출력: 최적 모델, 성능 리포트, 표현/피처 중요도 리포트, 실행 코드

#### 2) 재학습 트리거 및 배포 검증
 
- **Applicability domain(AD) 이탈** 감지 시 재학습 후보로 플래깅: AD는 QSAR 모델이 신뢰성 있게 예측할 수 있는 구조적 범위를 정의하며, k-NN 기반 유사도, reliability-density 등 여러 정의 방식이 존재한다 [7]. 다만 AD 추정 자체가 OECD가 지목한 QSAR 검증 원칙 중 가장 어려운 항목 중 하나로 꼽힐 만큼 방법론적으로 아직 표준화돼 있지 않다는 점은 설계 시 유의해야 한다 [7].
- **Active learning** 루프로 우선순위화된 신규 데이터가 일정 배치 수 쌓이면 재학습 트리거
- **Drift 확인**: 데이터 분포 변화(data drift, covariate shift)만으로 재학습하지 않고, 실제 성능 저하(concept drift, 즉 입력-출력 관계 자체의 변화)가 확인된 경우에만 실행. 이 구분은 실무 문헌에서도 강조되는데, data drift는 PSI·KS 검정 등으로 비교적 쉽게 탐지되는 반면 concept drift는 DDM·ADWIN 같은 별도 통계 기법으로 모델 오류율 변화를 직접 모니터링해야 한다는 점에서 원안의 "성능 저하 확인 후에만 재학습" 원칙과 일치한다 [8].
- **Champion-Challenger**: 재학습 모델은 기존 프로덕션 모델과 병렬 비교 후 통계적으로 유의한 개선이 있을 때만 교체. MLflow와 Databricks는 이 패턴을 별칭(champion/challenger alias) 기반으로 지원하며, 신규 모델을 보류 데이터셋에서 비교 평가한 뒤 기존 champion을 교체하는 구조를 표준 기능으로 제공한다 [9].
- **승인 및 기록**: 사람 최종 승인 후 MLflow Registry에 버전·비교 근거 전부 기록. MLflow Model Registry는 각 모델 버전을 학습에 사용된 run·데이터·파라미터와 연결해 재현성을 보장하고, 단계 승격마다 승인자를 기록하는 감사 이력을 제공하는 것이 문서로 확인된다 [10].

### 논의 필요성
 
- **자체 구축 vs 기존 도구 래핑**: 앞선 검토(코드 생성 컴포넌트 재검토)에서 확인했듯 QSARtuna, H2O AutoML 같은 성숙한 도구가 이미 탐색·CV·채택 자동화를 다루고 있어, 이 시스템을 처음부터 새로 구축하기보다 QSARtuna를 백엔드 탐색 엔진으로 채택하고 그 위에 도메인 특화 탐색공간·HITL 승인 계층만 얹는 것이 개발 비용 대비 근거가 더 명확하다.
- **AD 정의 방식의 선택**: k-NN 유사도, reliability-density, rivality/modelability index 등 여러 AD 정의가 경쟁하고 있고 아직 표준이 없으므로 [7], 어떤 정의를 채택할지, 혹은 여러 정의를 앙상블할지 결정이 필요하다.
- **Champion-Challenger 교체 임계값 사전 정의**: "통계적으로 유의한 개선"의 기준(p-value, 최소 효과 크기, 어떤 지표 기준인지)을 미리 정의해야 재학습 루프가 실제로 자동화된 의사결정으로 작동한다.
- **디스크립터 필터링과 RAG 근거의 결합 방식**: 앞선 Descriptor Selector 검토에서 지적된 대로, "애매함" 판정에 문헌 근거(RAG)를 활용할 경우 인용이 적은 통계적으로 유용한 디스크립터가 부당하게 배제될 위험이 있다. 이 시스템의 피처 선택 단계(VIF → Boruta/stability selection)는 순수 통계적 기준이므로 이 위험을 상당 부분 피하지만, 향후 문헌 근거를 판단 기준에 추가할 경우 통계적 중요도와 병행 판단하는 규칙이 필요하다.
- **해석 가능성 요구 수준의 정량화**: "해석 가능성 요구 수준"을 사용자 입력으로 받는다면, 이를 탐색공간 필터링 규칙(예: 요구 수준이 높으면 GNN/딥러닝 후보를 배제하고 descriptor 기반 모델만 탐색)으로 어떻게 변환할지 구체화가 필요하다.

### 확장 가능성
QSARtuna의 기능은 이미 매우 많은 부분을 자동화하고 있으며 오픈소스로 공개되고 있습니다.
- Optuna(하이퍼파라미터 최적화) + scikit-learn + RDKit + Chemprop(GNN 라이브러리)을 조합해서, 분자 표현 방식과 머신러닝 모델 조합을 자동으로 비교하고, 불확실성 정량화(uncertainty quantification)와 설명가능성(explainability)까지 기본 내장하고 있습니다.
- 해당 MLOps 파이프라인을 "불러오는 기능"만을 수행하는 Agent를 개발하는 것으로 프로젝트의 방향성을 수정을 고려하고 있습니다. 
- **트리거 관리**: 앞서 논의한 applicability domain 이탈 감지, active learning 배치 임계치 도달, 확인된 성능 저하 같은 신호를 모니터링하다가 QSARtuna를 호출하는 트리거 로직이 별도로 필요합니다. 이건 코드 생성이 아니라 "언제 API/CLI를 호출할지" 결정하는 스케줄링·모니터링 계층입니다.
- **데이터 준비/공급**: 내부 데이터베이스(ELN, 어세이 결과 저장소)에서 최신 데이터를 뽑아 QSARtuna가 요구하는 입력 포맷(SMILES + 라벨)으로 변환하는 파이프라인입니다. 이것도 코드를 매번 새로 쓰는 게 아니라, 한 번 만든 변환 스크립트를 반복 실행하는 것입니다.
- **Champion-Challenger 비교**: QSARtuna는 한 번 실행하면 "이번에 가장 좋은 모델"을 출력하지만, 지금 프로덕션에서 쓰이고 있는 기존 모델(champion)을 알지 못합니다. 통합 계층이 기존 champion을 불러와서, QSARtuna가 새로 낸 모델(challenger)과 동일한 held-out/신규 데이터로 나란히 평가하고, 성능 차이가 통계적으로 유의미한지 검정합니다. 유의미하지 않으면 그냥 기존 champion을 유지합니다.
- **사람 승인 및 감사 기록**: QSARtuna가 이미 계산해주는 불확실성 추정치와 설명가능성 결과(어떤 피처/표현이 왜 중요한지)를 사람이 보기 쉽게 정리해서 승인 요청을 띄우고, 승인 결과와 비교 근거를 MLflow 같은 레지스트리에 남깁니다.
